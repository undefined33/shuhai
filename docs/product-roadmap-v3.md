# ShuHai 产品路线图 v3

> 生效日期：2026-07-12  
> 状态：**已由 [`product-roadmap-v4.md`](./product-roadmap-v4.md) 取代，仅供产品复盘；正文保留当时决策**  
> 依据：[全方位审计](./audits/2026-07-12-comprehensive-product-security-ui-audit.md)与[生态调研](./research/2026-07-12-opencli-ecosystem-library-study.md)

## 1. 为什么重置路线

ShuHai 已开发一个多月，功能数量很多，但用户本人很少愿意使用。根因不是缺少 Provider、模板或诊断功能，而是：

- 一个简单工具被做成了管理后台，用户每次都要理解内部模块。
- 保存内容和维护书签两种频率、风险完全不同的任务混在同一界面。
- 破坏性书签操作与 Vault 写入仍有数据完整性缺口。
- 内容提取、AI 和 Markdown 处理边界主要靠自研字符串逻辑，长期安全维护成本过高。
- 旧文档仍将 Electron、SQLite、API 同步和更多 Goal 当作主线，会继续误导后续实现。

v3 不以“继续完成更多 Goal”为目标，而以“用户愿意连续使用且不丢数据”为目标。

## 2. 产品北极星

> ShuHai 是一个纯 Chrome 扩展：日常帮助用户把当前优质内容安全保存到 Obsidian，定期帮助用户整理和维护 Chrome 书签。

只有两个核心任务：

1. **保存当前内容**：文章、Twitter/X 帖子或微博。
2. **整理 Chrome 书签**：分类、重复项、失效链接和恢复。

### 非目标

- 不做 Electron 桌面应用或另一个安装包。
- 不在后台批量访问和归档任意书签网页。
- 不承诺完整同步 Twitter/X、微博账号中的所有收藏。
- 不依赖 Obsidian 社区插件或独立本地服务才能完成核心流程。
- 不把所有网页资源、脚本或远程图片原样离线归档。
- 不以支持更多 AI Provider、复杂模板或知识图谱作为近期卖点。

## 3. 产品形态

### 3.1 Toolbar Popup：每日保存

Popup 打开后只回答一个问题：“是否把当前页面保存到知识库？”

必须展示：

- 当前页面是否可提取及采用的提取方式。
- 标题、来源、内容摘要或结构化预览。
- 目标 Vault 相对路径和文件冲突策略。
- 可选标签与明确的“保存”按钮。
- 成功后的实际相对路径、失败原因和重试入口。

单条正常保存目标为两次点击以内，不经过队列。队列只服务批量、延后确认或失败恢复。

### 3.2 Side Panel：定期整理

Side Panel 是书签维护工作台：

- 书签概览与搜索。
- 规则优先、AI 补充的整理建议。
- 用户确认后应用，支持逐项结果和恢复。
- Basic/Standard/Strict 链接检查。
- 重复项和跟踪参数治理。

分类、健康检查和批量处理可以独立启动，不做强制线性向导；但每个任务内部必须有清晰的“准备 -> 运行 -> 复核 -> 应用 -> 恢复”状态。

### 3.3 Options Page：低频设置

Options Page 放置：

- Vault 目录授权、默认子目录和冲突策略。
- AI Provider、API Key、模型与连接测试。
- 本地规则、模板和高级参数。
- 操作日志、恢复、诊断导出与隐私清理。

高级功能默认折叠，不阻塞规则模式和不使用 AI 的用户。

## 4. 设计原则

1. **一屏一主任务**：Popup 只保存，Side Panel 只整理，Options 只设置。
2. **默认无损**：检测结果是建议，不是删除判决；AI 建议永不直接执行。
3. **可解释、可恢复**：用户看得见要改什么、改了什么、失败在哪里、怎么恢复。
4. **确定性优先**：规则、历史结果和缓存能完成的工作不调用 AI。
5. **失败可见**：禁止静默 fallback、静默覆盖、静默部分成功和伪成功 toast。
6. **最小权限**：在用户操作时申请完成该任务所需权限，说明原因并支持撤销数据。
7. **本地优先**：内容和操作日志保存在扩展本地或用户明确授权的 Vault；AI 只接收必要字段。
8. **不把品牌装饰当作可用性**：先做好层级、字体、间距、对比、速度和反馈。

## 5. 路线阶段

### Phase 0：文档和方向止损

状态：**本次完成**

- 建立 `docs/PROJECT_STATUS.md` 和 v3 路线图。
- 将旧 Electron spec、v2 路线和 Goal 001-031 标记为历史资料。
- 记录 OpenCLI、现成库和同类产品调研。
- 固定文档优先级和唯一可执行 Goal。

退出条件：新会话只读根文档即可知道当前产品形态、P0 风险和下一项工作。

### Goal 032：书签批量操作可恢复

状态：**IN_PROGRESS**（动态进度以 `docs/goals/README.md` 为准）

目标：建立持久化操作日志，正确表达 Chrome API 无事务条件下的准备、逐项成功、部分失败和恢复语义。

重点：

- 一个用户批次只生成一个操作记录和逆操作计划。
- 删除、URL 更新分别记录必要恢复字段。
- 只恢复实际成功的项，父目录缺失时进入明确 Recovery 文件夹。
- 重启 Side Panel 或 service worker 后仍可看到状态并恢复。
- 全量 JSON 快照只是灾备证据，不冒充一键恢复。

退出条件：破坏性批量操作的成功项 100% 有可验证的恢复路径。

### Goal 033：Vault 写入正确性

状态：**BLOCKED_BY_032**

目标：把写文件从“调用成功”提升为可靠的用户结果。

重点：

- 明确 `create`、`overwrite`、`skip`、`rename`、`error` 五种冲突结果。
- 默认不覆盖；同名文件先展示最终相对路径。
- 先写临时文件，再在能力允许范围内替换；无法原子替换时明确说明。
- 每个文件返回路径、字节数、策略、结果和错误。
- 保存成功后显示实际路径，并支持重试失败项。

退出条件：重复保存、同名冲突、权限失效、空间不足和部分失败均无静默丢失。

### Goal 034：运行时边界与持久化任务

状态：**BLOCKED_BY_033**

候选依赖：`zod`、`idb`，安装前重新核查并精确锁定版本。

目标：让 MV3 service worker 重启、旧存储和不可信消息不再破坏任务状态。

重点：

- 为消息、AI 输出、持久化记录和导入文件建立 schema。
- 使用版本化 IndexedDB schema 和迁移。
- 分类、健康检查、内容保存使用持久化 job 状态。
- 页面重新打开时恢复进度，而不是靠 React 局部状态。
- 存储损坏时 fail closed，并给出清理/导出诊断入口。

退出条件：service worker 中断后可以继续或安全终止任务，不出现幽灵进度。

### Goal 035：内容提取与 Markdown 安全 spike

状态：**RESEARCH_GATE**

候选：Defuddle、DOMPurify、Turndown、remark/rehype、`yaml`。

目标：在独立 spike 中比较“现有实现”和“现成组件管线”，不得直接替换生产逻辑。

必须验证：

- 文章质量：技术博客、长文、代码块、表格、选择文本。
- 社交内容：Twitter/X thread、quote、media；微博长文、转发。
- 安全：脚本、事件属性、`javascript:`、SVG、data URL、模板语法、Obsidian 可执行语法、YAML 注入。
- 资源预算：超大 DOM、深层嵌套、超长文本、海量图片。
- 隐私：Defuddle 必须关闭可能访问第三方服务的异步 fallback。

退出条件：fixture 质量和攻击测试都优于现有实现，且包体、许可、维护成本可接受，再写迁移 Goal。

### Goal 036：站点 Adapter 与提取可靠性

状态：**PLANNED**

目标：借鉴 OpenCLI 的 adapter、结构化结果和诊断思想，但保持纯扩展架构。

Adapter 契约至少包括：

- 站点标识、域名范围和能力。
- 输入、结构化输出 schema 和版本。
- 选择器/提取策略及明确 fallback。
- `unsupported`、`selector_changed`、`content_too_large` 等 typed error。
- fixture、分页/线程上限、去重和诊断脱敏。

不复制 OpenCLI 的内部 Twitter GraphQL、Cookie、bearer token 或动态 query id 逻辑。

退出条件：站点改版时用户收到可理解错误，开发者能用脱敏 fixture 复现，而不是悄悄保存错误正文。

### Goal 037：三界面 UI 重构

状态：**PLANNED**

目标：从 admin panel 变成高频浏览器工具。

重点：

- Popup 单任务、按需加载，目标 200ms 级可操作。
- Side Panel 使用工作台布局，不用卡片套卡片。
- Options 首屏只显示必要设置，高级设置折叠。
- 正文 13-14px，辅助信息不低于 12px；统一行高、间距和层级。
- 移除远程字体与装饰性“末字衬线”，建立本地系统字体方案。
- 关键状态有明确进度、完成、部分失败和恢复反馈。
- 键盘、焦点、屏幕阅读器和 reduced motion 通过检查。

退出条件：三条核心 E2E 在 popup/side panel/options 中无职责交叉，真实截图通过窄宽和深浅主题检查。

### Goal 038：规则优先的增量分类

状态：**PLANNED**

目标：减少 AI 成本、等待和不可预测建议。

重点：

- 稳定目录映射、用户规则、历史接受结果先命中。
- 只把未确定书签发送给 AI，并按预算分批。
- 不可信标题/URL 作为数据字段隔离，防止提示词注入。
- AI 输出必须 schema 校验，低置信度进入人工复核。
- 记录建议来源：规则、历史或 AI。

退出条件：AI 实际处理比例尽量低于 40%，建议接受率超过 70%，错误不触发自动移动。

### Goal 039：链接与重复项治理

状态：**PLANNED**

目标：把“HTTP 结果”转换为用户可理解的核实任务。

建议模式：

- Basic：只把 404/410 作为高可信失效候选。
- Standard：增加 DNS、明确连接失败和稳定重定向。
- Strict：增加超时、5xx、跨域跳转等低可信异常。

所有模式保留并发上限、同域间隔、暂停/继续和无凭据请求。`tldts` 只用于可注册域名分组，URL 安全解析继续依赖 `URL` 和 IP/网络策略。

重复项按协议、`www`、尾斜杠、片段和已知 tracking 参数做可解释归一化，原始 URL 永远可见。

退出条件：检查失败不再等同死链；用户可重试、打开核实、复制 URL、批量筛选，并看到判定依据。

### Goal 040：质量门禁与发布准备

状态：**PLANNED**

目标：停止依赖“单元测试全绿”来代表产品可用。

重点：

- Testing Library + `user-event` 覆盖核心交互。
- Playwright + axe 覆盖 popup、side panel、options。
- E2E：首次保存、批量整理并恢复、健康检查并处理。
- 包体、启动时间、长任务内存和大书签集性能基线。
- 权限文案、隐私说明、数据清理和第三方许可证清单。
- 两周 dogfood 记录失败原因和放弃步骤。

退出条件：达到第 7 节指标后，才讨论新功能。

## 6. OpenCLI 的位置

OpenCLI 不进入核心运行时。原因：它需要 Browser Bridge 扩展和本地 daemon，并依赖登录态浏览器自动化；这与 ShuHai 的单扩展、最小攻击面方向冲突。

可学习：

- 站点 adapter 契约。
- 结构化 JSON 输出。
- typed errors、诊断脱敏和 fixture 测试。
- 分页、去重和失控保护。

未来可选：在核心产品稳定后，支持导入**用户主动运行 OpenCLI 后导出的 JSON**。该入口必须离线、schema 校验、预览确认，且永不要求 ShuHai 代管 Cookie 或启动 daemon。

## 7. 产品验收指标

| 指标                     |                    目标 |
| ------------------------ | ----------------------: |
| 首次成功保存当前页面     |               30 秒以内 |
| Popup 正常保存           |   中位数不超过 2 次点击 |
| 静默文件覆盖/伪成功      |                       0 |
| 破坏性操作成功项可恢复率 |                    100% |
| 分类建议接受率           |                   > 70% |
| AI 处理本次范围比例      |              尽量 < 40% |
| 健康检查高可信失效误判率 |          测量并持续下降 |
| Popup 可操作时间         |           目标 200ms 级 |
| 核心 E2E                 |               至少 3 条 |
| 用户本人 dogfood         | 连续两周，每周至少 3 天 |

## 8. 变更控制

- 任一 Goal 开始前必须有独立 spec、精确文件范围、风险和验收证据。
- 只有 `docs/goals/README.md` 标记为 `READY` 的 Goal 可以开工；开工后转为 `IN_PROGRESS` 并继续执行。
- 新依赖必须先做“必要性、许可证、体积、维护、安装脚本、安全公告、替代方案”记录。
- 安全库只是一个层，不得将 Defuddle、DOMPurify、Zod 或 OpenCLI 宣传成完整安全边界。
- 新需求若不直接提升两条核心任务，应进入 backlog，不得插队。
