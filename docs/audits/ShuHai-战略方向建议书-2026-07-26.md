# ShuHai 战略方向建议书

> 日期:2026-07-26
> 来源:外部审计会话(Claude)第二轮输出——第一轮《ShuHai 审计建议书 2026-07-26》回答"现状哪里有问题",本文回答"接下来该往哪走"
> 读者:项目 owner 与 Codex / 编排 agent
> **性质声明:本文是方向性输入,不是执行合同,不构成任何实施授权。** 按 `AGENTS.md` 的 Goal Control 规则,agent 读完本文后的正确动作是:据此起草 Goal `DRAFT` 引用本文条目编号,交 owner 审阅推进;不得直接修改业务代码。

## 0. 一句话总判断

**代码已经不欠这个项目什么了,现在欠的是使用。** 本文六条建议全部围绕一个转向:把项目的重心从"生产被验证的软件"移到"验证软件值得存在"。

---

## S1. 最大风险:项目正在变成流程纪念碑 → 两周 dogfood 冻结

**判断(直白版)**:仓库里关于"如何开发"的证据浩如烟海——43 份 Goal 合同、四轮独立评审、逐字节核对的 disposable Vault;而关于"真的在用"的证据,只有几次 5-10 条的探针测试。到今天为止,这几万行代码产出的全部用户价值,是一个测试 Vault 里的 5 个文件。owner 造出了一台能生产"被验证软件"的漂亮机器,但还没有当过这个软件的用户。

**建议动作**:

1. 前置:先完成审计建议书 P0-1(safe-readable 渲染 v2)与 P0-3 中的图标项——不可读的笔记没有 dogfood 价值。
2. 之后**功能冻结两周**:不新增任何业务 Goal,owner 每天在真实 Vault 上使用两条旅程(X 收藏同步 + Chrome 书签整理)。
3. 建立 `docs/dogfood/2026-XX-friction-log.md`:每天记录日期、摩擦点、严重度(挡路 / 烦人 / 小瑕疵),以及一栏对照问题(见 S6)。
4. 两周结束后,由摩擦日志——而不是任何 roadmap 想象——产出接下来的 3-5 个 Goal 草案。日志里没出现的功能,不立项。

**验收标准**:两周后存在 ≥10 天的日志条目;下一批 Goal 的每一条都能引用日志行号。这同时就是 Goal 047(RESEARCH_GATE)要求的"两周真实使用数据"。

## S2. 评审体系的结构性盲区:连续全零 PASS 是警报,不是荣誉

**判断(直白版)**:内部评审 Dalton、Carver、Locke 一轮轮给出 "PASS,P0/P1/P2 均为 0",而一次外部审计在**核心交付物**上一个下午找到了 P0(笔记不可读且内容被改写)。这不是 reviewer 不认真——是整套门禁验证的都是"符合合同",没有任何一道要求"以用户身份读一篇产出的笔记"。渲染函数的每个测试都过了,但没有人真的看过那篇笔记长什么样。真实的评审几乎总能找到点什么;连续全零本身就该触发怀疑。

**建议动作**(修订 `docs/workflows/verification-and-acceptance.md`):

1. **Reviewer 强制配额**:每次独立 review 至少提出 3 条改进建议(任意级别),或逐条论证为什么一条都没有。"P0/P1/P2 = 0" 不再是可直接接受的完整结论。
2. **产品真相环节**:每 2-3 个 Goal 强制一次——评审者(或 owner)端到端使用一遍产出物,以用户身份写下"最烦的三个点",无论是否在合同范围内,全部进 backlog。
3. Review 报告新增固定小节:"我作为用户实际看到/用到了什么",不允许以测试通过代替。

## S3. 流程分轨:重仪式用在贵的地方

**判断(直白版)**:045 阶段的重仪式是划算的——碰 Vault、书签、权限的地方犯错很贵。但接下来是产品打磨期,UI 文案、渲染模板、交互细节需要"试→看→调"的快循环;两万字合同会杀死它。安全纪律的价值在于用在对的地方,而不是均匀涂满。

**建议动作**(修订 `AGENTS.md` §3 或新增 workflow 文档,明确两条轨道):

| 轨道 | 范围 | 流程 |
| --- | --- | --- |
| **硬轨** | Vault 写入、书签 mutation、权限与 host permission、消息/Port/storage 边界、迁移 | 保持现状:完整 Goal 合同 + mock 门禁 + 独立评审 + 真实 QA |
| **软轨** | UI 布局与文案、渲染模板、交互细节、图标与视觉、文档 | 小 PR + 截图/目视验收 + lint/typecheck/test 通过即可合并;单 PR 限定文件清单,不需要独立评审轮 |

判定规则写死:一个改动只要触碰硬轨清单中的任一文件域,整个 PR 走硬轨。软轨不豁免安全底线(AGENTS.md §6 不可变),豁免的只是仪式。

## S4. 安全投入再平衡:从"永不断裂"转向"断裂便宜"

**判断(直白版)**:部署形态是"owner 自己的浏览器、自己的数据"。真实边界是三个:页面 DOM 输入、写进 Obsidian 的 markdown、权限面——当前强度值得保持。但比如对自己扩展写入的 IndexedDB 行做恶意迁移防御(约 1300 行,见审计 P1-1),防的是此形态下几乎不存在的攻击者。而真正高价值的"安全"工作是另一种:**x.com 改 `data-testid` 是"何时"而非"是否"的问题**,让 scraper 的断裂变得便宜,比让它永不断裂更能延长产品寿命。

**建议动作**:

1. 承接审计 P1-1:v3 定为 schema 基线,删除 v1/v2 迁移路径。
2. 新增一个轻量 workflow:**fixture 刷新流程**——每 4-6 周(或每次 X 改版报错后)从真实收藏页导出一份脱敏 DOM fixture,替换 `tests/fixtures/x-bookmarks.ts` 的来源快照,跑 adapter 测试比对。
3. 为断裂设 SLO 而不是防御:目标"从发现选择器失效到修复合入 < 半天"。现有 extractor-diagnostics 已提供发现能力,缺的只是这条修复路径的演练。
4. 硬轨清单(S3)即为安全强度的保留区;清单之外不再新增防御纵深型代码。

---

## S5. 平台战略:克制批量同步,放开单条保存

**判断(直白版)**:每接一个平台的**批量同步**,就是签下一条永久的选择器跑步机;单人项目撑不起三条。而**单条保存**(在详情页保存当前内容)便宜一个数量级、易泛化,才是适合多平台铺开的形态。

**建议动作**:

1. 明确写入 roadmap:批量收藏同步**封顶 2 个平台**;单条保存可按平台逐个 spike 扩展(每个仍走 GO/NO_GO 门禁,但合同走 S3 软轨+硬轨混合的最小版本)。
2. 微博:只评估**官方开放平台的收藏读取接口**这一条路线;DOM 扫描的 `NO_GO` 维持,不复议。评估结论直接决定 Goal 044 的生死。
3. **受监督 backfill 模式**(新 Goal 候选):当前 `LIMITED_GO` 的 10 条/批预算,意味着几百条存量收藏要手动跑几十次——首次入库体验会劝退 owner 自己。建议新增一种模式:预算放大但仍有界(例如 50 条/批 × 用户逐批确认继续),复用现有 checkpoint / pause / resume / catalog 去重,不改任何安全语义,只改预算档位与续跑体验。日常增量同步维持 10 条紧预算不变。

## S6. AI 的唯一明确高价值位置:把"堆"变成"库"(暂缓,但立对照)

**判断(直白版)**:修好可读性之后,如果 dogfood 两周里 owner 仍然从不打开那些笔记,原因会是"一堆推文不等于知识"。那才是 AI 真正该上场的位置:每条笔记一行摘要 + 2-3 个主题标签,写入 frontmatter,让 Obsidian 的搜索、Dataview 和图谱真正可用。这不违背"AI 只建议、用户确认"的原则,输入有界(单条正文)、输出有界(一行 + 标签),是 AI 在这个产品里唯一明显赚回成本的地方。

**建议动作**:

1. **现在不实施。** 在 S1 的摩擦日志里加一栏固定对照问题:"如果这条笔记有一行摘要和标签,我今天会不会用到它?"
2. 两周后统计该栏:多数天为"会" → 立项(硬轨,因为写 frontmatter 属于 Vault 写入);多数为"不会" → 永久搁置,省下一整条功能线。
